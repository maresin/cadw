## 0. Общая цель

PINGIS должен выполнить **двухэтапную миссию**:

1. **Аудит и исправление** существующего кода (баги, нарушения RAM-лимита, неэффективные алгоритмы).
2. **Продолжение разработки** по roadmap (Phase D: 29 алгоритмов P1, v0.9.31–v0.9.36).

**Нельзя** переходить к этапу 2, пока этап 1 не закрыт с зелёными тестами.

**Главное ограничение всего проекта:** ≤1 батч данных в RAM. Всё тяжёлое — через примитивы `Reduce` / `HashShuffle` / `Sort`. Любой код, который материализует больше одного батча или игнорирует `MemoryGuard.check_batch()`, считается **дефектом**, даже если тесты проходят.

## 1. Этап 0: Аудит (read-only)

### 1.1. Bug hunt

PINGIS должен самостоятельно искать баги, **не полагаясь на существующие тесты** (тесты могут быть неполными). Обязательные зоны проверки:

| Зона | Что искать |
|---|---|
| `cadw/core/memory_guard.py` | Формулы `state_limit`, `check_batch`, `check_state`; правильность `extra_factor`; переполнение `int`; обработка `None`/`0` |
| `cadw/ops/reduce.py`, `shuffle.py`, `sort.py` | Граничные случаи: пустые батчи, один батч, null-ключи, дубликаты, смена схемы между батчами |
| `cadw/ops/groupby.py`, `join.py`, `dedup.py`, `rank.py`, `quantile.py`, `resample.py`, `pivot.py` | Утечки памяти через `to_pylist()` без guard; O(N²) алгоритмы; материализация целых колонок |
| `cadw/dataframe/*.py` (18 модулей после B.1) | Нарушения контракта: `.as_py()`, row-loops, `import pandas`; потеря фильтров; неправильный `__len__`/`shape` |
| `cadw/ml/*.py` | Численная стабильность (деление на 0, логарифм 0, переполнение `exp`); сходимость; единообразие логов |
| `cadw/ts/*.py` | Утечки состояния между группами; некорректная обработка сезонности; `NaN` propagation |

**Методы поиска (PINGIS выбирает сам):**
- Статический анализ: `ruff`, `pyright`, `pylint` (уже в dev-зависимостях), AST-сканирование на запрещённые паттерны (`.to_pylist()` без `check_batch`, `.as_py()`, `iterrows`).
- Динамический: property-based testing (`hypothesis` — добавить в dev-зависимости), fuzzing на малых данных.
- **Сравнение с эталоном:** для каждого алгоритма — прогон на синтетических данных и сравнение с `pandas`/`scikit-learn`/`statsmodels` (только для валидации, **не для импорта**).
- Ручной code review критических путей.

**Результат этапа 0.1:** `AUDIT_REPORT_v0930.md` со списком находок. Для каждого бага:
- Класс (критический / функциональный / RAM-нарушение / стиль)
- Воспроизведение (минимальный пример)
- Влияние на контракт (какой инвариант нарушен)
- Предлагаемое исправление
- **Приоритет:** P0 (блокирует RAM-гарантию), P1 (неверный результат), P2 (edge case)

### 1.2. RAM-аудит (критично)

Отдельный проход по всему коду на предмет:

1. **`to_pylist()` / `to_pandas()` / `to_numpy()` без guard.** Каждый вызов должен быть либо внутри `check_batch(extra_factor=...)`, либо в белом списке (`cadw/patch_utils.py::WHITELISTED_FUNCS`) с обоснованием. Проверить, что белый список **не расширен** новыми записями без причины.
2. **Материализация целой колонки.** Например, `arr = b.column(c)` с последующим `len(arr)` — допустимо (O(1) metadata), но `arr.to_pylist()` — уже материализация. Искать паттерны, где целая колонка копируется в Python-list перед обработкой.
3. **Рекурсивные вызовы без ограничения глубины.** `_per_group_apply`, `groupby` — могут рекурсивно материализовать группы.
4. **`state_bytes` занижен.** Проверить все `ReduceOp.state_nbytes()` — не врут ли они (например, `__slots__` с mutable-полями).
5. **`external_sort` fan-in.** `compute_fan_in()` — учитывает ли реальный размер буфера, а не только количество файлов.
6. **`MemoryGuard.calibrate()`** — реально ли срабатывает, или это заглушка.

**Инструмент:** прогнать `scripts/bench_v0919_calibration.py` на синтетических данных (N=10k, 100k, 1M строк) с `MemoryGuard(max_memory_mb=10)` — зафиксировать фактические пики RSS через `psutil`, сравнить с `pred_total`. Расхождение >2× — баг.

### 1.3. Аудит эффективности алгоритмов

Для каждого публичного алгоритма в `cadw/ops/` и `cadw/ml/`:

1. **Асимптотика.** Задокументирована ли? Совпадает ли с реальной? Найти скрытые O(N²) (например, `for` по батчам с `pd.concat` внутри).
2. **Константы.** Сколько памяти на строку? Сколько CPU на батч?
3. **Сравнение с эталоном.** Прогнать на 1M строк, сравнить с `pandas`/`polars`/`scikit-learn` (только как reference, не импорт). Зафиксировать: время, пик RAM.
4. **Альтернативы.** Для каждого алгоритма, где текущая реализация медленнее или прожорливее эталона, — предложить альтернативу (с обоснованием: asymptotic + benchmarks из интернета + ссылка на источник).

**Результат этапа 0.3:** `EFFICIENCY_AUDIT_v0930.md` с таблицей:

| Алгоритм | Asymptotic | Peak RAM/row | Bench (1M) | Alternative | Why better | Source |
|---|---|---|---|---|---|---|

**Правило замены:** PINGIS может заменить алгоритм из roadmap только если:
- Альтернатива **строго лучше** по asymptotic или по RAM-константе.
- Есть **публичный бенчмарк** (paper, blog, docs библиотеки) с подтверждением.
- Новая реализация **не хуже** по функциональности (все edge cases покрыты).
- Замена **обоснована** в PR/коммите со ссылкой.

## 2. Этап 1: Исправление

### 2.1. Приоритеты

1. **P0 — RAM-нарушения.** Немедленно. Блокируют гарантию out-of-core.
2. **P1 — функциональные баги.** Неверные результаты, потеря данных, исключения на валидных входах.
3. **P2 — эффективность.** Замена алгоритмов, оптимизация констант.

### 2.2. Процесс исправления

Для каждого бага/оптимизации:
1. **Написать тест, который падает** (или показывает разницу в RAM/времени). **Честный тест** — не подстраиваться под текущее поведение, а проверять контракт.
2. **Исправить код.**
3. **Убедиться, что тест зелёный.**
4. **Прогнать полный fast suite** (`pytest -q -m "not slow"`).
5. **Прогнать RAM-бенчмарк** (`bench_v0919_calibration.py`) — убедиться, что пик не вырос.
6. **Закоммитить** с описанием: что было, что стало, почему.

### 2.3. Требования к тестам

**Тесты должны быть честными:**
- Проверять **контракт**, а не текущую реализацию.
- Не использовать `assert result == expected_from_current_impl` — использовать `assert result == expected_from_pandas` (или другой эталон).
- Не подстраивать `expected` под то, что выдаёт CADW. Если CADW выдаёт X, а pandas — Y, и контракт говорит «как pandas», — тест падает, код правится.
- Property-based тесты: `@given(st.lists(st.integers()))` — проверять инварианты (сумма, количество, монотонность).
- Для RAM: проверять пик RSS через `psutil` внутри теста, сравнивать с `MemoryGuard`-предсказанием (допуск 2×).

**Нельзя:** удалять/ослаблять существующие тесты без обоснования (если тест был неверным — обосновать в коммите).

### 2.4. Логи обучения моделей

Для всех моделей в `cadw/ml/` (linear, logistic, kmeans, pca, gbdt, naive_bayes, **и новых в Phase D**):

1. **Единый интерфейс логов:**
   ```
   [fit] <model_name> | iter=N/M | loss=X.XXXXXX | state_bytes=B | rss=Y MiB
   ```
2. Логи должны быть **опциональными** (флаг `verbose` или env `CADW_LOG=1`), но **включены по умолчанию** в тестах — чтобы видеть сходимость.
3. Для iterative-моделей (GBDT, logistic, kmeans): логировать каждую итерацию/бустинг-раунд.
4. Для one-shot (linear via normal eq, PCA, naive_bayes): логировать финальный `loss` (или `train_acc`).
5. Формат — **structured** (JSON lines) или простой text — на выбор PINGIS, но **единый** для всех моделей.

**Результат этапа 1:** список коммитов, `AUDIT_REPORT_v0930.md` обновлён статусами (fixed/wontfix/backlog).

## 4. Этап 3: Phase D (разработка)

### 4.1. Приоритеты

Phase D — 29 items. Начинать с **D.1.1 IForest** (P0/S), затем **D.1.3 cost-GBDT** (S), **D.1.4 fairness** (S), **D.6.3 permutation importance** (S), **D.6.5 h3/hexbin** (S), **D.6.7 LinUCB** (S), **D.6.8 GMM density** (S), затем M/L.

**PINGIS может менять порядок**, если видит, что какой-то алгоритм быстрее/полезнее, но должен обосновать в PR.

### 4.2. Требования к каждому алгоритму

1. **Implementation:** `cadw/ml/<name>.py` или `cadw/ops/<name>.py`.
2. **Interface:**
   - Модели: `class <Name>Model` + `fit_<name>(df, ...) -> <Name>Model`.
   - Модель имеет `.predict(df)`, `.score(df)` (или `.transform`).
3. **RAM:** O(state) state между батчами; никакой материализации целого датасета. Каждый `check_batch` — с правильным `extra_factor`.
4. **Tests:** ≥8 тестов на алгоритм:
   - Synthetic data: известный результат.
   - Reference comparison: `pandas`/`sklearn`/`statsmodels` (для валидации).
   - Edge cases: пустой вход, один элемент, все null, дубликаты.
   - Determinism: same seed → same result.
   - RAM: пик RSS ≤ 2× prediction.
   - Multi-batch: chunk=1 vs chunk=1000 — same result.
5. **Logs:** следуют единому формату (см. 2.4).
6. **Docs:** добавить в `docs/decisions/` секцию с описанием алгоритма, сложности, RAM-константы.
7. **CHANGELOG:** запись в `### v0.9.31` (или соответствующую версию).

### 4.3. Правила работы с алгоритмами

**PINGIS активно использует интернет:**

1. **Документация:** для каждого алгоритма — изучить документацию библиотеки-эталона.
2. **Бенчмарки:** искать публичные бенчмарки (papers, blog posts, docs) на эффективность (время, память). Использовать как evidence для выбора алгоритма.
3. **Paper trail:** для каждого алгоритма — ссылка на источник (paper, docs) в docstring.
4. **Воссоздание, а не импорт:** реализовывать алгоритм самостоятельно на примитивах CADW. **Можно** заимствовать код из открытых источников (MIT/Apache/BSD), но:
   - С указанием источника в docstring.
   - С адаптацией под out-of-core парадигму (нельзя просто скопировать sklearn-код, который грузит всё в память).
5. **Замена алгоритма из плана:** если PINGIS нашёл более эффективную альтернативу — заменить, но:
   - Обосновать: asymptotic, RAM-константа, benchmark.
   - Ссылка на источник.
   - Не хуже по функциональности.
   - Зафиксировать в PR/коммите.
6. **Добавление своих алгоритмов:** PINGIS может добавить алгоритм, не указанный в roadmap, если он:
   - Решает задачу, востребованную в out-of-core контексте.
   - Не дублирует существующий.
   - Обоснован в PR.
7. **RAM — всегда первый критерий.** Если алгоритм быстрый, но требует O(N) RAM — отклонить или переделать на out-of-core.

### 4.4. Процесс разработки

Для каждого алгоритма:
1. **Research:** docs + benchmarks + papers.
2. **Design:** RAM-модель (state_size, batch_factor), API (fit/predict/score), edge cases. Записать в `docs/decisions/` **до** кода.
3. **Implement:** на примитивах CADW (`ReduceOp`, `external_sort`, `hash_shuffle`).
4. **Test:** 8+ тестов (см. 4.2.4), property-based где возможно.
5. **Bench:** 1M rows, сравнить с эталоном (время + RAM), зафиксировать в `EFFICIENCY_AUDIT_v0930.md`.
6. **Commit:** с описанием, ссылками, bench-результатами.

**Нельзя:** коммитить алгоритм без тестов и без RAM-бенчмарка.

## 7. Правила коммуникации

- **Не молчать:** для каждого крупного решения (замена алгоритма, архитектурное изменение) — писать в PR/коммит **обоснование**.
- **Не подстраиваться под тесты:** если тест падает — сначала выяснить, что неверно (тест или код). Если тест — исправить тест с обоснованием. Если код — исправить код.
- **Не расширять белый список** (`WHITELISTED_FUNCS`) без обоснования. Каждая новая запись — с указанием, почему `to_pylist`/`to_pandas` безопасен.
- **Не использовать `import pandas`** в `cadw/ops/` или `cadw/dataframe/` (только в тестах как reference).
- **Не материализовать больше одного батча** — это нарушение главного контракта.
