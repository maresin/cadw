## Снимок контекста CADW (май 2026)

### 1. Цели и принципы фреймворка

- **Главная цель**: обработка больших данных (не помещающихся в RAM) на слабых локальных машинах, без использования GPU и распределенных хранилищ.
- **Ключевая проблема**: операции, требующие shuffle (группировка, join), которые не могут быть выполнены в памяти. Наш фреймворк должен решать их с контролируемым потреблением RAM и сбросом на диск.
- **Принципы**:
  - **Накопление данных в памяти запрещено**; любые временные данные должны быть либо чанкованными, либо сбрасываться на диск.
  - Immutability (кэшируемые результаты неизменяемы).
  - Единый потоковый интерфейс ввода-вывода (`BatchReader`, `BatchWriter`).
  - Pandas-подобный API для пользователя.
  - Apache Arrow – основной формат данных в памяти и для кэша.

### 2. Текущее состояние проекта

#### Реализованные компоненты (проверены тестами)
- `MemoryGuard` – расчет лимитов памяти и размеров батчей.
- `BatchReader`/`BatchWriter` для Parquet и Arrow IPC.
- `SpillManager` – сброс агрегатов на диск (пока на основе `pickle`, работает, но не оптимален).
- `UniqueCollector` – сбор уникальных значений.
- `GroupByAggregator` – группировка с `sum`, `mean`, `count`.

#### Отсутствующие или недоделанные компоненты
- `CadwDataFrame` – основная структура данных.
- `VirtualOperationManager` – ленивые операции (срезы, фильтры).
- Интеграция примитивов с `CadwDataFrame`.
- Сквозные тесты (e2e) с реальным контролем памяти.
- Поддержка индексов (в планах).
- Логирование (не внедрено).

### 3. Архитектурное видение (итоговое)

#### Уровни (снизу вверх)
1. **Хранение**: Parquet (исходные данные) и Arrow IPC (кэш, shuffle-партиции).
2. **Потоковый ввод-вывод**: `BatchReader`/`BatchWriter`.
3. **`CadwDataFrame`**: хранит колонки как `dict[str, pyarrow.ChunkedArray]`, управляет индексом, содержит `VirtualOperationManager`.
4. **Операции**: `unique`, `groupby`, `join` – используют `CadwDataFrame.to_batches()` и `SpillManager`.
5. **Пользовательский API**: pandas-подобный (`head`, `__getitem__`, `groupby`, `write_parquet` и т.д.).

#### Ключевые архитектурные решения
- Ленивые срезы и фильтры (без материализации).
- Двухпроходный shuffle для группировки (индексы → партиции → агрегация).
- Контроль памяти через `MemoryGuard` (динамический `batch_size`, лимиты словарей).
- Индекс: виртуальный `RangeIndex` по умолчанию, материализуется при `set_index`.

   - Хранение колонок как `ChunkedArray`.
   - `to_batches()` – простой итератор по чанкам.
2. **Добавить `VirtualOperationManager`** и поддержку срезов.
3. **Интегрировать `UniqueCollector` и `GroupByAggregator`** через `df.to_batches()`.
4. **Написать e2e тест** с искусственно малым лимитом памяти, проверяющий корректность и сброс на диск.
5. **Внедрить логирование**.
6. **Улучшить `SpillManager`**: перейти на Arrow IPC вместо pickle, байтовый контроль.

### 5. Принятые решения
- Не использовать `pd.DataFrame` внутри – строим собственные Arrow-структуры.
- Не реализовывать распределённую обработку (только локальная).
- Отказаться от сложных индексов на первом этапе.
- Копировать pandas API, но не реализацию.

### 6. Риски и открытые вопросы

- Работа с очень большими группами (миллионы уникальных ключей).
- Совместимость с pandas (ожидания пользователей).
